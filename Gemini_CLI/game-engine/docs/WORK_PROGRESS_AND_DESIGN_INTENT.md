## 1. プロジェクトの目的と基本理念

### 1.1. 教育用エンジンとしての位置付け
商用のゲームエンジン（Unreal Engine, Unity, Godot 等）は内部が高度に最適化されている反面、コードベースが巨大で、初学者が内部構造（グラフィックス API の制御やシーングラフの仕組み）を追うことは困難です。
一方、最小限のサンプルコード（API チュートリアルなど）は、1 つの関数やファイルにすべてがベタ書きされていることが多く、実用的なエンジンアーキテクチャ（責務分離、ライフサイクル管理）を学ぶ橋渡しになりません。

本プロジェクトは、中高生やゲームエンジン開発初学者が**「読みやすく、構造が美しく、なぜそのように書くのかを理解できる」**状態を目指して構築されています。

### 1.2. コア哲学 (Core Philosophy)
1. **Readability & Learnability First（可読性と学びやすさ最優先）**
   - 過度なビット演算、手動メモリアライメントの過剰パック、過剰な SIMD 組み込み命令による可読性の低下を避ける。
   - 1 クラス 1 責務を原則とし、巨大な「God Class」を作らない。
2. **Godot-inspired Simplicity（Godot に学ぶ明快な階層構造）**
   - シーンを「ノードの木構造（Composite パターン）」で表現し、あらゆるゲーム要素（カメラ、メッシュ、スクリプトノード）を同一のインターフェースで統括する。
3. **Explain the "Why"（理由の明確化）**
   - DirectX 12 固有の専門用語（Command Allocator, Fence, Resource Barrier など）には、必ず「現実世界の比喩」や「なぜそれが必要か」の注釈をコード内に残す。

## 2. アーキテクチャ全体像

エンジンは大きく **Core / Graphics / Scene** の 3 つの層に分離されています。

```
+-------------------------------------------------------------------+
|                            Game Scene                             |
|  [Main Scene / User Nodes (RotatorNode, SatelliteCube, etc.)]     |
+-------------------------------------------------------------------+
                                  |
                                  v
+-------------------------------------------------------------------+
|                           Scene Layer                             |
|  - Node (Composite パターン, ライフサイクル, QueueFree)           |
|  - Node3D (Transform3D, 階層ワールド行列の再帰合成)               |
|  - Camera3D (View / Projection 行列計算)                          |
|  - MeshInstance3D (メッシュ形状・バッファ参照保持)                |
+-------------------------------------------------------------------+
                                  |
              [Extract パス: RenderItem 描画パケットを抽出]
                                  v
+-------------------------------------------------------------------+
|                          Graphics Layer                           |
|  - GraphicsDevice (Device, CommandQueue, Allocator, List, Fence)  |
|  - SwapChain (Double Buffering, RTV, VSync)                       |
|  - DepthBuffer (DSV, Z-Buffer による前後深度判定)                 |
|  - Shader & Pipeline (HLSL 実行時コンパイル, PSO, RootSignature)  |
|  - Vertex / Index / ConstantBuffer (Upload Heap, Persistent Map)  |
+-------------------------------------------------------------------+
                                  |
                                  v
+-------------------------------------------------------------------+
|                            Core Layer                             |
|  - Window (Win32 API ラッパー, RAII, PeekMessage ループ)           |
+-------------------------------------------------------------------+
```

### 1 フレームの処理フロー: 4 段階パイプライン
毎フレームの処理は、以下の 4 つのフェーズに厳格に分離されています。

```
[1. Update (論理更新)]
    └── SceneTree::Process(delta)
        └── 各 Node の OnProcess(delta) を呼び出し（位置更新、自転・公転等）
            ↓
[2. Extract (描画パケット抽出)]
    └── SceneTree::ExtractRenderItems()
        └── 各 MeshInstance3D から Transform とバッファ参照を RenderItem 配列へ抽出
            ↓
[3. Execute (描画コマンド記録・発行)]
    └── CommandList->Reset()
    └── リソースバリア（Present -> RenderTarget）
    └── ClearRenderTargetView, ClearDepthStencilView
    └── PSO / RootSignature / Viewport / Scissor のセット
    └── 抽出された RenderItem ごとに MVP 行列を定数バッファへ書き込み -> DrawIndexedInstanced
    └── リソースバリア（RenderTarget -> Present）
    └── CommandQueue->ExecuteCommandLists() & SwapChain->Present(1) & Fence 同期
            ↓
[4. Cleanup (遅延解放)]
    └── SceneTree::Cleanup()
        └── フレーム中に QueueFree() されたノードを安全に delete 一括回収
```

## 3. Phase 1: DirectX 12 レンダリング基盤の構築とその意図

DirectX 12 は DirectX 11 と異なり、ドライバが行っていたメモリ管理や CPU-GPU 同期、ステート管理をアプリケーション側が明示的に行う必要があります。初学者が最も挫折しやすいこの部分を、明快なクラス群に分割して実装しました。

### 3.1. ウィンドウ & メインループ (`Window`)
- **意図**: Win32 API の C 言語風コールバック構造（`WNDPROC`）を、現代的 C++ の RAII クラスで安全にカプセル化する。
- **工夫**:
  - ウィンドウ作成時（`WM_CREATE`）に `CREATESTRUCT` 経由で `this` ポインタを渡し、`SetWindowLongPtr(hwnd, GWLP_USERDATA, ...)` でウィンドウと C++ インスタンスを紐付け。
  - 静的プロシージャから安全にメンバ関数プロシージャへ転送することで、グローバル変数を完全排除。
  - `PeekMessage` によるノンブロッキングなポーリングループを採用し、ゲーム特有の連続フレーム更新を実現。

### 3.2. DirectX 12 コアデバイスと同期機構 (`GraphicsDevice`)
- **意図**: GPU との通信窓口と、コマンド記録・発行・完了待ちの責務を単一クラスに集約する。
- **実装内容**:
  - `ID3D12Device`: GPU の論理表現。リソースやパイプラインの生成工場。
  - `ID3D12CommandQueue`: GPU 側の実行キュー。
  - `ID3D12CommandAllocator`: コマンドリストが記録に使うメモリプール。
  - `ID3D12GraphicsCommandList`: コマンドを記録するノート。
  - `ID3D12Fence`: **CPU と GPU の同期信号機**。
- **設計意図 (Why)**:
  - GPU は CPU と非同期（遅れて）並列実行されます。前フレームの描画が終わっていないのにアロケータをリセット（白紙に戻す）するとクラッシュします。
  - そのため、毎フレーム `Fence->SetEventOnCompletion` によるシンプルな GPU 完了同期待ち（`WaitForGpu()`）を挟むことで、初学者にとって動作順序が直感的に追えるシングルフレーム同期を採用しました。
  - デバッグレイヤー（`ID3D12Debug`）を初期化の最先頭で有効化し、API の不正使用を Visual Studio の出力ウィンドウで即座に警告できるようにしています。

### 3.3. スワップチェイン & ダブルバッファリング (`SwapChain`)
- **意図**: 画面のチラつき（ティアリング）を防ぎ、スムーズな画面表示を行う。
- **実装内容**:
  - バッファ数 2（フロントバッファとバックバッファ）のダブルバッファリング。
  - レンダーターゲットビュー（RTV）ディスクリプタヒープの管理。
  - `Present(1)` による垂直同期（VSync = 60fps 固定）の有効化。
- **リソースバリアの意図**:
  - DirectX 12 では、画像メモリの状態（表示用 `PRESENT` か、描画書き込み用 `RENDER_TARGET` か）を明示的に GPU に伝える必要があります。
  - `ResourceBarrier` を挟むことで、GPU パイプラインのハザード（書き込み中の読み取り等）を完全に防止しています。

### 3.4. シェーダパイプライン (`Shader` & `Pipeline`)
- **意図**: グラフィックスパイプラインのステート管理を整理し、HLSL シェーダの読み込みを柔軟にする。
- **実装内容**:
  - `Shader`: `D3DCompileFromFile` を用いて、起動時に `shaders/SimpleTriangle.hlsl` を動的コンパイル。
    - コンパイルエラー時には、HLSL の行番号・エラーメッセージを標準エラー出力へ分かりやすくフォーマット表示する設計。
  - `Pipeline`:
    - **ルートシグネチャ**: 定数バッファをルートパラメータ 0（`b0`）として直接バインド（ルート記述子方式）。
    - **ラスタライザ**: 背面カリング（`D3D12_CULL_MODE_BACK`）を有効化し、見えない裏面ポリゴンを自動スキップ。
    - **ブレンドステート**: 不透明描画の標準設定。
    - **深度ステンシルステート**: 深度テスト（`D3D12_COMPARISON_FUNC_LESS`）と深度書き込みを有効化。

### 3.5. バッファリソースとメモリ配置
メモリヒープの特性を理解しやすいよう、バッファを用途に応じて適切に分離しました。

| バッファ種別 | ヒープタイプ | CPUアクセス | 採用理由と設計意図 |
| :--- | :--- | :--- | :--- |
| **VertexBuffer** | `UPLOAD` | 書込可 (CPU $\rightarrow$ GPU) | 初学者向けに中間バッファの複雑さを省き、CPU から直接書き込める Upload Heap を使用。 |
| **IndexBuffer** | `UPLOAD` | 書込可 (CPU $\rightarrow$ GPU) | 16bit (`DXGI_FORMAT_R16_UINT`) を採用し、メモリ消費と頂点再利用を両立。 |
| **ConstantBuffer** | `UPLOAD` | 永続マップ (Persistent Mapping) | 毎フレーム行列を更新するため、`Map` したままアンマップしない永続マップ方式を採用（オーバーヘッド最小化）。**DirectX 12 の 256 バイトアライメント要件**をヘルパー関数で自動計算。 |
| **DepthBuffer** | `DEFAULT` | 不可 (GPU 専用 VRAM) | 深度バッファは GPU 内部の超高速アクセスが必須なため、CPU アクセス不能な Default Heap に配置。クリア値（Depth=1.0f）を指定して初期化。 |

#### なぜルート記述子（Root CBV）を採用したのか？
定数バッファの参照方法には「ディスクリプタヒープ方式（CBV Heap）」と「ルート記述子方式（SetGraphicsRootConstantBufferView）」があります。
本エンジンでは、ディスクリプタヒープのインデックス割り当てやヒープ管理の複雑さを初学者が抱え込まないよう、GPU 仮想アドレス（`GetGPUVirtualAddress()`）を 1 行で直接渡せる**ルート記述子方式**を採用しました。

### 3.6. 3D キューブ描画
- **頂点構造**: 位置（`FLOAT3`）と頂点カラー（`FLOAT4`）を持つシンプルな構造。
- **立方体定義**:
  - サイコロの 6 面をそれぞれ独立した 4 頂点（合計 24 頂点）、36 インデックスで構築。
  - 面ごとに鮮やかな固有色（赤・シアン・緑・黄・青・マゼンタ）を割り当て、後続のライティング実装前でもキューブの回転と陰影・立体感がはっきりと視覚認識できるように工夫。

## 4. Phase 2: Godot 風シーン・ノード構造の構築とその意図

DirectX 12 でキューブが 1 個描画できるようになった次の段階として、「ゲームエンジン」として多重オブジェクトや階層構造、スクリプト動作を扱えるアーキテクチャを導入しました。

### 4.1. Composite パターンによる基底 `Node` クラス
- **意図**: 「1 つのオブジェクト」と「オブジェクトの階層ツリー」を同じ型（`Node`）として均一に操作できるようにする。
- **実装**:
  - `Node` は `std::vector<std::unique_ptr<Node>> children_` を持ち、ツリー構造を形成。
  - `AddChild()` で子ノードを追加すると、自動的に親ポインタ（`parent_`）がセットされる。

### 4.2. メモリ所有権モデル (`unique_ptr` + 生ポインタ)
C++ 初学者が最も嵌まりやすい「メモリリーク」と「循環参照による解放不能」を言語仕様レベルで防止する厳格な所有権ルールを策定しました。

```
[親ノード (Parent)]
    │
    │  std::unique_ptr<Node>  (排他的な完全所有権: 親が死ねば子も死ぬ)
    ▼
[子ノード (Child)]
    │
    │  Node* raw pointer     (所有権を持たない単なる参照: 循環参照を完全排除)
    ▼
[親ノード (Parent)]
```

- **親 $\rightarrow$ 子**: `std::unique_ptr<Node>`
  - 親が子の排他的所有権を持つ。親がデストラクトされれば、すべての子孫ノードも再帰的に安全・確実に delete される。
- **子 $\rightarrow$ 親**: 生ポインタ `Node*`（または後述の参照）
  - 親へのアクセスは必要だが、所有権は持たない。`std::shared_ptr` を双方向に持たせることによるメモリリーク（参照カウントが 0 にならず解放されない問題）を根本から排除。

### 4.3. 統一ライフサイクルとボトムアップ `OnReady`
ゲームオブジェクトが安全に協調動作できるよう、Godot エンジンを手本とした 4 段階のライフサイクルを導入しました。

1. **`OnEnterTree()`**: ノードがシーンツリーに参加した瞬間に呼ばれる（トップダウン）。
2. **`OnReady()`**: 自分と**すべての子ノードの準備が完了した直後**に呼ばれる（**ボトムアップ**）。
   - **意図**: 親ノードの初期化コード内で `GetChild<T>()` を呼んだ際、「子ノードがまだ初期化されていない」という順序バグを撲滅する。子が全員揃ってから親の `OnReady` を発火させる。
3. **`OnProcess(float delta)`**: 毎フレームのロジック更新。
4. **`OnExitTree()`**: ツリーから離脱する直前に呼ばれる（終了処理・後始末）。

### 4.4. 安全な遅延削除 (`QueueFree`)
- **なぜ即座に `delete` してはいけないのか？**
  - ノードの `OnProcess` ループ（ツリーを走査している最中）で誰かが直接 `delete` や `children_.erase()` を呼ぶと、反復処理中のイテレータが無効化（Iterator Invalidation）され、不正アクセスクラッシュが発生します。
- **解決策**:
  - 削除要求時はフラグ（`is_queued_for_deletion_`）を立てるだけの `QueueFree()` を呼ぶ。
  - 1 フレームのすべての更新・描画抽出が完了した末尾の `SceneTree::Cleanup()` フェーズで、削除予約フラグの立ったノードを一括回収・解放する。

### 4.5. シーングラフと 3D 階層トランスフォーム (`Transform3D` & `Node3D`)
- **数学的意図**:
  - ローカル行列は $S$ (拡大縮小) $\times$ $R$ (回転: Pitch/Yaw/Roll) $\times$ $T$ (平行移動) の順で合成。
- **階層ワールド行列の再帰合成**:
  - `Node3D::GetWorldMatrix()` は、自分のローカル行列に「親が `Node3D` であれば親のワールド行列」を再帰的に掛け算します：
    $$M_{\text{world}} = M_{\text{local}} \times M_{\text{parent\_world}}$$
  - これにより、「親が回転・移動すると、子ノードも親の重心を中心に連動して公転・移動する」シーングラフの基本挙動を数学的に実現しました。

### 4.6. カメラノード (`Camera3D`)
- **意図**: カメラを「特別なグローバル変数」ではなく、シーンツリーのどこにでも配置できる通常のノード（`Node3D` の派生）として扱う。
- **実装**:
  - カメラの **View 行列** は、カメラ自身のワールド行列の**逆行列**（`XMMatrixInverse`）として算出。
    - *なぜ逆行列か？*: 「カメラが右を向く」ことは「世界全体を左に回転させる」ことと同義だからです。
  - **Projection 行列** は視野角（FOV）、アスペクト比、ニア/ファークリップ面から透視投影行列を算出。

### 4.7. 描画分離アーキテクチャ (`RenderItem` / Update-Extract-Execute)
ゲームエンジン設計における最大の原則の 1 つが**「ロジック（Scene）と描画（Graphics）の完全分離」**です。

- **禁止事項**:
  - `Node::OnProcess` の中で `command_list->DrawIndexedInstanced(...)` などの DirectX 12 固有 API を直接呼び出すこと（密結合）。
  - もしノードが描画 API を直接叩くと、DirectX 12 以外のバックエンド（Vulkan や Metal）への対応や、将来的なマルチスレッド描画、シャドウマップ用パスの追加が不可能になります。
- **解決策**:
  - `MeshInstance3D` は論理ノードとして存在し、描画フェーズになると純粋なデータ構造体 `RenderItem` を生成して返します：
    ```cpp
    struct RenderItem {
        DirectX::XMFLOAT4X4 world_matrix;         // ワールド変換行列
        const VertexBuffer* vertex_buffer = nullptr; // 頂点バッファ
        const IndexBuffer* index_buffer = nullptr;   // インデックスバッファ
    };
    ```
  - メインループ側は、集められた `std::vector<RenderItem>` を順に取り出して GPU コマンドを発行するだけになります。

### 4.8. 階層構造の動作検証 (`Main.cpp`: 自転・公転サンプル)
Phase 2 の集大成として、以下のシーンツリーを構築し、設計通りの階層連動・描画分離が動作することを実証しました。

```
Root (Node)
 ├── MainCamera (Camera3D) - (0, 3, -6) から原点を見下ろす
 └── ParentCube (RotatorNode: 自転) - 原点に配置
      └── ChildCube (SatelliteCube: 公転) - 親から (2.5, 0, 0) オフセット配置
```

- `ParentCube` が自転すると、その子である `ChildCube` は親のローカル座標軸に従って親の周りを綺麗に公転。
- `ChildCube` はさらに自身も逆回転しながら公転するため、親子関係の行列乗算（$M_{\text{local}} \times M_{\text{parent\_world}}$）が正しく機能していることが視覚的に証明されました。

## 5. Dear ImGui デバッグ UI の統合とその意図

ゲームエンジンの開発において、3D 空間上のオブジェクトの位置やカメラの視野角（FOV）、階層構造を視覚的に確認・調整できる「インスペクタ」や「シーンヒエラルキー」は不可欠なツールです。本プロジェクトでは、業界標準のデバッグ GUI ライブラリ **Dear ImGui** を導入しました。

### 5.1. FetchContent による外部ライブラリ自動管理
- **意図**: ユーザーや学習者がリポジトリを clone した際、手動で zip を解凍して配置したり環境変数を設定する煩雑さを排除する。
- **実装**:
  - CMake の `FetchContent` モジュールを用いて、CMake 実行時に GitHub の公式リポジトリ（`v1.91.8`）からソースを自動取得。
  - プロジェクト内で静的ライブラリ（`imgui`）としてコンパイル・リンクすることで、完全なポータビリティを実現しました。

### 5.2. DirectX 12 における専用 SRV ディスクリプタヒープの役割
- **なぜ専用ヒープが必要か？**:
  - ImGui はフォントやアイコンのテクスチャを画面に描画するため、シェーダから参照できる **SRV (Shader Resource View)** が最低 1 つ必要になります。
  - DirectX 12 では、シェーダが参照するディスクリプタは必ず `D3D12_DESCRIPTOR_HEAP_FLAG_SHADER_VISIBLE` フラグが付いたディスクリプタヒープ上に存在しなければなりません。
- **実装**:
  - `ImGuiLayer` 内部で `D3D12_DESCRIPTOR_HEAP_TYPE_CBV_SRV_UAV`（要素数 1）の専用ディスクリプタヒープを生成・保持。
  - 描画時に `command_list->SetDescriptorHeaps(...)` で GPU に提示してから ImGui バックエンドの描画関数（`ImGui_ImplDX12_RenderDrawData`）を呼び出します。

#### 【重要】初期化構造体 (`ImGui_ImplDX12_InitInfo`) と `CommandQueue` の必須性
- Dear ImGui 1.91.x 以降の DirectX 12 バックエンドでは、初期化時に内部でフォントテクスチャの GPU アップロード用コマンドを発行するため、`CommandQueue` が必須となります。
- 旧来の `ImGui_ImplDX12_Init(device, buffer_count, ...)` は `CommandQueue` を受け取らないため、内部で `cmdQueue == nullptr` によるアクセス違反クラッシュを引き起こします。
- そのため、最新仕様である `ImGui_ImplDX12_InitInfo` 構造体に `Device`, `CommandQueue`, `NumFramesInFlight`, `RTVFormat`, `SrvDescriptorHeap` を明示的にセットして初期化する設計としています。

### 5.3. Window メッセージフックによる入力委譲
- **意図**: GUI 操作のマウスクリックやキー入力を安全に ImGui に渡しつつ、UI を操作している最中にゲーム側の操作が誤発火しないようにする。
- **実装**:
  - `Core::Window` クラスに汎用コールバック `CustomWndProcHandler` を設置。
  - `ImGui_ImplWin32_WndProcHandler` をフックし、ImGui が入力を消費した場合（`io.WantCaptureMouse` / `io.WantCaptureKeyboard`）は Windows 標準のイベント処理に委譲せず早期リターンさせることで、UI とゲームロジックの入力分離を実現しました。

### 5.4. シーンヒエラルキーとリアルタイムインスペクタの実装意図
- **シーンヒエラルキー (`DrawNodeHierarchy`)**:
  - `SceneTree` のルートノードから子ノードを再帰的に巡回し、`ImGui::TreeNodeEx` で木構造を直感的に可視化。
  - ノード種別（`[Cam]`, `[Mesh]`, `[3D]`, `[Node]`）を動的キャストで判別してプレフィックス表示。
  - 右クリックメニューから `QueueFree()` を実行できるショートカットを配置。
- **インスペクタ (`DrawInspector`)**:
  - 選択されたノードの名前変更。
  - `Node3D` のトランスフォーム（位置・回転・拡縮）をスライダーでリアルタイム編集。
    - *工夫*: 内部ではラジアンで保持される回転角を、ユーザーが直感的に理解しやすい**度数法（Degrees: 0°〜360°）**に相互変換して表示。
  - `Camera3D` の FOV（視野角）スライダーによるパースペクティブの動的変更。

## 6. Phase 3: リソース管理システムの実装とその意図

3D ゲームにおいて、メッシュデータ（頂点バッファ・インデックスバッファ）や画像テクスチャ、マテリアルは膨大なメモリ（VRAM）を消費します。もしオブジェクト（`MeshInstance3D`）が生成されるたびに新しいバッファを作成していると、あっという間にメモリが枯渇します。本フェーズでは、Godot エンジンの核となる **Resource 構造** と **Flyweight パターン** を導入しました。

### 6.1. Godot 風 Resource 思想と Node との責務分離
- **Node（シーン要素）**:
  - ゲーム空間における「位置（Transform）」「親子構造」「振る舞い（Process）」を担います。
  - 親が子を排他的に所有する（`std::unique_ptr`）。
- **Resource（データ要素）**:
  - 純粋なアセットデータ（3D 幾何形状、テクスチャ、シェーダ）を担います。
  - 空間的な位置を持たず、複数のノードから共有利用される（`std::shared_ptr`）。

### 6.2. Flyweight パターンと std::weak_ptr キャッシュの仕組み
- **課題**:
  - 単に `std::shared_ptr` でキャッシュマップを保持すると、一度ロードしたリソースの参照カウントが常に 1 以上になり、誰も使わなくなってもメモリから破棄されない（メモリリーク）問題が発生します。
- **解決策**:
  - `ResourceLoader` のキャッシュに **`std::weak_ptr<Resource>`** を使用：
    ```cpp
    std::unordered_map<std::string, std::weak_ptr<Resource>> cache_;
    ```
  - **ロード時**:
    1. キャッシュから `weak_ptr.lock()` を試みる。
    2. 他のノードが使用中であれば、有効な `std::shared_ptr` が返り**即座に共有（重複生成防止）**。
    3. 未ロードまたは全員が手放して破棄済みであれば、新規生成してキャッシュに `weak_ptr` を登録。
  - **破棄時**:
    - すべてのノード（`MeshInstance3D`）が `QueueFree()` やデストラクトにより解放されると、`std::shared_ptr` の参照数が 0 になり、**自動的にデストラクタが呼ばれて GPU メモリ（VRAM）から安全に解放**されます。

### 6.3. MeshInstance3D のリファクタリングと共有効果
- 以前は `VertexBuffer*` と `IndexBuffer*` の生ポインタを渡していましたが、`std::shared_ptr<Resource::Mesh>` を保持する設計へ刷新しました。
- サンプルシーンでは、自転する親キューブ（`MainCube`）と公転する子キューブ（`SatelliteCube`）が、`ResourceLoader::GetOrLoad` を介して同一の `"builtin://Mesh/Cube"` リソースを共有しています。
- これにより、ノード数が増えても VRAM 上のキューブメッシュは 1 つ分しか確保されません。

### 6.4. ImGui によるリソースキャッシュの可視化
- `Resource Monitor` ウィンドウを追加し、現在キャッシュに登録されているリソースのパスと、**外部参照数（`use_count`）をリアルタイムに表形式で監視**できるようにしました。
- ノードが生きている間は参照数がカウントされ、ノードを `QueueFree()` すると参照数が減算される様子を視覚的に体験・デバッグできます。

## 7. Phase 4: マテリアル & ライティング機能の実装とその意図

これまでの段階では、3D キューブの各面に直接原色を指定して描画していました。しかし、現実世界の立体感や質感（光沢・影）を表現するには、光と物体の相互作用を計算する**ライティング（Lighting）**と材質を定義する**マテリアル（Material）**が不可欠です。

### 7.1. 法線ベクトル (Normal) による面の向きの定義
- **なぜ法線が必要か？**:
  - 光が当たったときに「面がどれくらい光の方を向いているか」を計算するには、面の直交ベクトル（法線 $\vec{N}$）が必要です。
- **実装**:
  - `Graphics::Vertex` 構造体に `normal` (Nx, Ny, Nz) を追加。
  - 立方体の 6 面に対して、それぞれ外側を向く単位法線ベクトル（前面なら $(0, 0, -1)$、上面なら $(0, 1, 0)$ 等）を割り当てました。
  - 頂点シェーダ（`Lit.hlsl`）内でワールド行列の回転成分（$3 \times 3$ 部分行列）を掛けることで、キューブが自転・公転しても常に正しいワールド空間法線が得られるようにしています。

### 7.2. ライティングの三要素: Ambient・Lambert Diffuse・Blinn-Phong Specular
シェーダ（`shaders/Lit.hlsl`）には、3D グラフィックスの古典的かつ最も直感的な 3 つの反射モデルを組み込みました。

1. **環境光 (Ambient Light)**:
   - 光源が直接当たらない影の部分も完全に真っ黒にならず、周囲からの照り返しを模して全体を均一に照らします。
2. **拡散反射 (Diffuse / Lambert)**:
   - ランバートの余弦則に基づき、面の法線 $\vec{N}$ と光源方向 $\vec{L}$ の内積 $\max(\vec{N} \cdot \vec{L}, 0)$ から明るさを算出。
   - 光に対して正面を向く面は明るく、斜めを向く面は滑らかに暗くなります。
3. **鏡面反射 (Specular / Blinn-Phong)**:
   - 視線方向 $\vec{V}$ と光源方向 $\vec{L}$ のハーフベクトル $\vec{H} = \frac{\vec{L} + \vec{V}}{\|\vec{L} + \vec{V}\|}$ を計算。
   - 法線 $\vec{N}$ との内積の累乗 $(\max(\vec{N} \cdot \vec{H}, 0))^{\text{power}}$ からハイライト（鋭い光沢ツヤ）を白く加算。

### 7.3. DirectionalLight3D ノードによる平行光源の表現
- **意図**: 太陽光のように無限遠から一定方向に降り注ぐ平行光を、通常のノード（`Node3D` の派生）としてシーングラフに配置できるようにする。
- **実装**:
  - ノードの回転姿勢（Transform3D）の前方ベクトルから光線方向を自動算出。
  - 光源色（Color）、光源強度（Intensity）、環境光（Ambient Color）のプロパティを保持。

### 7.4. Material リソースと定数バッファ (SceneConstantData) の統合
- `Material` リソース（`src/Resource/Material.hpp`）により、材質色（Albedo）、光沢の鋭さ（Specular Power）、反射強度（Specular Intensity）をパラメータ化。
- ノードごとに異なるマテリアル（光沢キューブ、金色衛星、マットな地面）を適用し、描画時に単一の定数バッファ `SceneConstantData`（208 バイト / 256 バイトアライメント）に詰め込んで GPU へ転送する構造としました。

### 7.5. ImGui によるリアルタイム光線・材質デバッグ
- インスペクタから `DirectionalLight3D` を選択すると、**光の色・強度・環境光**をリアルタイムに変更できます。
- `MeshInstance3D` を選択すると、**材質カラー（カラーピッカー）や光沢スライダー**を動かすことで、表面のハイライトの鋭さがリアルタイムに変化する様子をインタラクティブに観察できます。

## 8. Phase 5: 入力管理システム & フライトカメラの設計意図

### 8.1. なぜ入力抽象化クラス (Core::Input) が必要か？
ゲーム開発において、OS（Win32）の低レベルなメッセージ（`WM_KEYDOWN`, `WM_MOUSEMOVE` 等）や `GetAsyncKeyState` API を個々のゲームオブジェクトやカメラから直接叩くと、以下の致命的な問題が発生します：
1. **OS 依存の密結合**: Windows 以外の環境（Linux や WebAssembly 等）への移植が極めて困難になる。
2. **フレームレート・ポーリングの不整合**: ウィンドウ非アクティブ時にも入力を誤検知したり、フレーム間の変化（「押された瞬間」「離された瞬間」）の検出が困難。
3. **UI（ImGui）との入力競合**: デバッグ UI をクリック・ドラッグしている最中に、ゲームのキャラクターやカメラが勝手に動いてしまう（操作の干渉）。

`Core::Input` クラス（`src/Core/Input.hpp`）は、これらの問題を解決するために以下の設計を採用しました：
- **3 状態の明確な区別**:
  - `IsKeyHeld` / `IsMouseButtonHeld`: 現在キーまたはボタンが押されているか（長押し検知）
  - `IsKeyPressed` / `IsMouseButtonPressed`: 今フレームで新たに押された瞬間か（トリガー検知）
  - `IsKeyReleased` / `IsMouseButtonReleased`: 今フレームで離された瞬間か（リリース検知）
- **フレーム間デルタの安全な集約**:
  - `GetMouseDelta()` により、前フレームからの相対移動量 $(dx, dy)$ を取得。
  - `GetMouseWheelDelta()` により、ホイールの回転ノッチ数を取得。
  - 毎フレーム先頭で `Input::NewFrame()` を呼ぶことで、移動量デルタを自動リセット。
- **Godot 風の直感的な便利ヘルパー**:
  - `GetAxis(negative, positive)`: 1 次元の軸入力（-1.0, 0.0, 1.0）
  - `GetVector(left, right, down, up)`: 2 次元の正規化移動ベクトル。斜め移動時にも速度が $\sqrt{2}$ 倍に加速せず、長さ 1.0 に自動クランプ。
- **フォーカス喪失時の安全ガード**:
  - ウィンドウが非アクティブ化された際（`WM_ACTIVATE` / `WM_KILLFOCUS`）、すべての押下フラグを安全にリセットし、キーの「押しっぱなしバグ」を完全防止。

### 8.2. ImGui との入力調停アーキテクチャ
`Core::Window` のメッセージコールバックにおいて、ImGui とゲーム側入力の調停を以下のように多段構造で実現しました：
```
[ Win32 OS メッセージ ]
         │
         ▼
[ ImGuiLayer::HandleWin32Message ] ──── (UI操作で消費された場合) ──→ [ 完了・ゲーム側をブロック ]
         │ (未消費の場合)
         ▼
[ Core::Input::ProcessMessage ] ──→ [ ゲーム側入力バッファ更新 ]
```
これにより、インスペクタのスライダーをドラッグしたりテキストを入力している間はカメラが一切反応せず、3D ビューポートをクリック・ドラッグした時だけカメラが旋回するという、プロフェッショナルなゲームエンジンと同等の洗練された操作性を獲得しました。

### 8.3. FlightCamera3D ノードによる自由な視点移動
- **意図**: 3D シーン内のオブジェクトの陰影変化やマテリアルの光沢ハイライトを、あらゆる角度・距離から自由自在に観察できるようにする。
- **実装（`src/Scene/FlightCamera3D.hpp`）**:
  - `Camera3D` を継承し、ノードのライフサイクルメソッド `OnProcess(float delta)` 内で更新を実行。
  - **右ボタンドラッグ**: 視線回転（水平ドラッグで Yaw 旋回、垂直ドラッグで Pitch 首振り）。
    - ジンバルロックや画面反転を防ぐため、上下首振り角度を $-89^\circ \sim +89^\circ$ に制限。
  - **WASD キー**: カメラの向き（`GetForward()`, `GetRight()`）に沿った 3D 平行移動。
  - **E / Space キー / Q / C キー**: 上昇・下降。
  - **Left Shift キー**: 高速移動ブースト（2.5倍速）。
  - **マウスホイール**: 移動スピードのリアルタイム増減（0.5 〜 50.0 単位/秒）。
- **数学的設計**:
  - `Transform3D` および `Node3D` に、回転行列から直接ワールド空間の基底ベクトルを取り出す `GetForward()`, `GetRight()`, `GetUp()` を追加。
  - 行列の Row 2 が Forward、Row 0 が Right、Row 1 が Up を表すという DirectXMath（行優先）の数学的性質をそのまま活用した、初学者にとって線形代数の良い教材となる設計。

## 9. 現代的 C++ (C++20) のプラクティス

初学者が現代の標準的な C++ を学べるよう、古いイディオム（生ポインタ `new/delete` の乱用、マクロ定数など）を排除し、C++20 の機能を積極的に採用しています。

## 9. Phase 6: テクスチャマッピング機能の設計意図

### 9.1. DirectX 12 におけるテクスチャ転送の仕組み（Upload Buffer と 256 バイト行アライメント）
DirectX 12 でテクスチャを描画する際、DirectX 11 や OpenGL のように「メモリ上のピクセル配列を関数1つで即座にテクスチャ化する」ことはできません。
効率と GPU アーキテクチャの真の動作を学ぶため、本エンジンでは以下の厳密なパイプラインを採用しました：

1. **Default Heap（VRAM 専用メモリ）の確保**:
   - 高速なレンダリングのため、テクスチャ本体は GPU 専用の `D3D12_HEAP_TYPE_DEFAULT` メモリに配置します。
   - このメモリには CPU から直接アクセス（書き込み）できません。
2. **中間アップロードバッファ (Upload Heap) と 256 バイト行ピッチアライメント**:
   - DirectX 12 の仕様として、テクスチャの各行（Row Pitch）は **256 バイトの倍数** (`D3D12_TEXTURE_DATA_PITCH_ALIGNMENT`) にアライメントされている必要があります。
   - `device->GetCopyableFootprints()` を呼び出すことで、必要なメモリフットプリントとパディングサイズを自動算出し、CPU メモリから中間バッファへ安全に行単位コピーを行います。
3. **GPU コピーコマンドとリソースバリア**:
   - `CopyTextureRegion` コマンドを発行し、中間バッファから Default Heap へデータを高速転送。
   - リソースバリアを発行し、テクスチャの状態を `D3D12_RESOURCE_STATE_COPY_DEST` から `D3D12_RESOURCE_STATE_PIXEL_SHADER_RESOURCE` へ明示的に遷移させます。
4. **一回限りコマンドの同期 (Fence) と中間メモリ自動解放**:
   - コマンドキューに投入後、`ID3D12Fence` を使って GPU のコピー完了を待機。
   - 転送完了後、中間アップロードバッファはスコープアウトして自動解放され、GPU 専用メモリだけが残る無駄のないメモリライフサイクルを実現しました。

### 9.2. スタティックサンプラーの採用理由
サンプラー（テクスチャの拡大縮小補間やタイリング方法を定義するオブジェクト）は、動的ディスクリプタヒープから渡すこともできますが、本エンジンではルートシグネチャの **スタティックサンプラー (Static Sampler)** を採用しました。
- **Why?**:
  - サンプラー用のディスクリプタヒープ管理を完全に省略できる。
  - ルートシグネチャに 1 行記述するだけで、ピクセルシェーダの `SamplerState g_sampler : register(s0)` に直接バインドされる。
  - バイリニア補間（`MIN_MAG_MIP_LINEAR`）と Wrap アドレスモード（タイリング繰り返し）により、遠くのテクスチャもチラつかず滑らかに表示される。

### 9.3. 白テクスチャフォールバックによる「シェーダ分岐排除」の美学
テクスチャの有無を判定するためにピクセルシェーダ内で `if (has_texture)` のような動的分岐を行うと、GPU のワープ（Wavefront）内でスレッドの分岐ペナルティ（Branch Divergence）が発生します。
本エンジンでは：
- デフォルトで **1x1 の純白テクスチャ (0xFFFFFFFF)** を用意し、テクスチャ未設定のマテリアルには自動的にこれをバインド。
- ピクセルシェーダ内では常に `g_texture.Sample(g_sampler, input.texcoord)` を実行。
  - 白テクスチャの場合、サンプリング結果は $(1.0, 1.0, 1.0, 1.0)$ となるため、マテリアル色・頂点カラーに一切影響を与えない。
- これにより、テクスチャあり・なしのオブジェクトが同一のパイプライン・同一のシェーダで高速に描画できる、プロの現場でも多用される洗練された設計となっています。

### 9.4. プロシージャルテクスチャファクトリの提供
外部の画像ファイル（PNG/JPG）を読み込む `CreateFromFile` に加え、外部画像がなくても即座に 3D 空間の奥行きや回転を実感できるよう、以下のプロシージャルテクスチャ生成関数を用意しました：
- `CreateCheckerboard`: 地面用の市松模様（白と濃灰のスレートパターン）。床に貼ることでフライトカメラ移動時の距離感が劇的に向上。
- `CreateBoxGrid`: キューブ用の枠線・木箱風パターン。回転時の面の動きが明瞭に視認可能。

## 10. Phase 7: シャドウマッピング（リアルタイム影生成機能）の実装とその意図

### 10.1. 影がもたらす空間把握と 2 パスレンダリングの必然性
3D グラフィックスにおいて、陰影（Shading: 物体自体の明暗）だけでは「物体が空中に浮いているのか」「地面に接地しているのか」を正確に認識することが困難です。
他の物体によって光が遮られて落ちる影（Shadow）が存在することで、初めて鑑賞者は**「物体の高さ・距離感・接地感」**を直感的に把握できます。

リアルタイムレンダリングにおける最も標準的かつ高速な影生成手法が **シャドウマッピング (Shadow Mapping)** です。本エンジンではこれを **2 パスレンダリング** として設計・実装しました：

```
【パス 1: シャドウパス (Shadow Depth Pass)】
  平行光源視点からシーンを描画 ────> 深度テクスチャ (ShadowMap 2048x2048) に遮蔽距離を記録
                                              │
                                              ▼
【パス 2: メインカラーパス (Main Lit Color Pass)】
  カメラ視点からシーンを描画 ────────> 各ピクセルでライトからの距離とシャドウマップを比較
                                       ・手前に遮蔽物がある ──> 影 (Direct Light 減衰)
                                       ・遮蔽物がない     ──> 光が当たる
```

- **なぜシャドウパスでピクセルシェーダを使わないのか？**:
  - パス 1 で必要なのは「頂点の幾何学的な深度（Z値）」のみであり、テクスチャ色やライティング計算は一切不要です。
  - `ShadowPipeline` ではピクセルシェーダを `nullptr`（不使用）に設定し、カラーレンダーターゲットを 0 個 (`NumRenderTargets = 0`) にすることで、GPU のラスタライザが最速で深度バッファに書き込む「超高速デプスプリパス」を実現しています。

### 10.2. Typeless テクスチャ (R32_TYPELESS) の理由: DSV 書き込みと SRV 読み取りの両立
DirectX 12 において、シャドウマップを実装する際に多くの開発者が直面する最大の壁が「リソースフォーマットの決定」です。
- パス 1（シャドウパス）: 深度ステンシルビュー (DSV) として **深度書き込み (`DXGI_FORMAT_D32_FLOAT`)** を行いたい。
- パス 2（メインパス）: シェーダリソースビュー (SRV) として **ピクセルシェーダ読み取り (`DXGI_FORMAT_R32_FLOAT`)** を行いたい。

もしテクスチャ生成時に `Format = DXGI_FORMAT_D32_FLOAT` と固定してしまうと、DirectX 12 ではそのリソースに対してカラー/データ読み取り用の SRV を作成することができません。
そのため、リソース本体は **型なし (`DXGI_FORMAT_R32_TYPELESS`)** としてメモリ確保します：

```cpp
// テクスチャ本体: メモリ領域として 32bit 浮動小数点分を確保（解釈は型なし）
tex_desc.Format = DXGI_FORMAT_R32_TYPELESS;
tex_desc.Flags = D3D12_RESOURCE_FLAG_ALLOW_DEPTH_STENCIL;

// DSV 作成時: 「この 32bit は深度 (D32_FLOAT) として書き込む」と解釈
dsv_desc.Format = DXGI_FORMAT_D32_FLOAT;

// SRV 作成時: 「この 32bit はシェーダから赤色成分 (R32_FLOAT) として読み取る」と解釈
srv_desc.Format = DXGI_FORMAT_R32_FLOAT;
```
これにより、1 つのテクスチャリソースをパス 1 で深度書き込み、パス 2 でテクスチャサンプリングするという完全な再利用が可能になります。

### 10.3. D3D12 の制約克服: 単一共有 SRV ディスクリプタヒープによるテクスチャ共存
DirectX 12 には以下の厳格な API 制約が存在します：
> **「1 つのコマンドリストに対して同時に SetDescriptorHeaps できる CBV_SRV_UAV ヒープは最大 1 つである。」**

前フェーズ（Phase 6）では各 `Texture2D` が自律的に 1 スロットのヒープを保持していましたが、メインパスでは「アルベドテクスチャ (`t0`)」と「シャドウマップ (`t1`)」を**同一のドローコール内で同時にシェーダに渡す**必要があります。

本エンジンでは、教育用としての明快さと API 制約の解決を両立するため、以下の設計を採用しました：
1. `Main.cpp` 側で描画用の **単一シーン共有 SRV ディスクリプタヒープ (`scene_srv_heap`)**（16 スロット）を確保。
2. `ShadowMap` および `Texture2D` に `CreateShaderResourceViewInHeap(device, cpu_handle, gpu_handle)` を追加。
   - スロット 0: シャドウマップ SRV
   - スロット 1: デフォルト白テクスチャ SRV
   - スロット 2: チェッカーボードテクスチャ SRV
   - スロット 3: 木箱グリッドテクスチャ SRV
3. メインパスの先頭で `scene_srv_heap` を 1 回だけバインドし、シャドウマップの GPU ハンドル (`t1`) をルートパラメータ 2 にセット。
4. 各メッシュの描画時にマテリアル対応テクスチャの GPU ハンドル (`t0`) をルートパラメータ 1 にセット。

この設計により、ヒープの切り替えコストをゼロにし、API 違反を起こさずに複数のテクスチャを柔軟にピクセルシェーダで組み合わせることが可能になりました。

### 10.4. ハードウェア比較サンプラーと 3x3 PCF によるソフトシャドウ
ナイーブなシャドウマッピングでは、テクスチャ解像度の限界により影のエッジがギザギザ（ジャギ）になります。
本エンジンでは、**ハードウェア比較サンプラー** と **PCF (Percentage Closer Filtering)** を組み合わせて映画のような滑らかなソフトシャドウを実現しています。

#### 1. ハードウェア比較サンプラー (`D3D12_FILTER_COMPARISON_MIN_MAG_LINEAR_MIP_POINT`)
ルートシグネチャのスタティックサンプラー 1 (`register(s1)`) に比較サンプラーを指定：
- `ComparisonFunc = D3D12_COMPARISON_FUNC_LESS_EQUAL;`
- `BorderColor = D3D12_STATIC_BORDER_COLOR_OPAQUE_WHITE;` (範囲外は深度 1.0 = 光が当たる)
HLSL 内で `SampleCmpLevelZero` を呼ぶと、GPU ハードウェアが内部で **「深度の比較」と「近傍 2x2 テクセルのバイリニア補間」** を 1 命令で同時に実行します。

#### 2. 3x3 PCF フィルタリング
ピクセルシェーダ内でサンプリング位置を中心とする $3 \times 3$ のグリッド（計 9 点）で比較サンプリングを行い平均化：
```hlsl
float shadow_sum = 0.0f;
for (int y = -1; y <= 1; ++y)
{
    for (int x = -1; x <= 1; ++x)
    {
        float2 offset = float2(x, y) * texel_size;
        shadow_sum += g_shadow_map.SampleCmpLevelZero(
            g_shadow_sampler,
            shadow_uv + offset,
            current_depth - bias
        );
    }
}
float lit_ratio = shadow_sum / 9.0f;
shadow_factor = lerp(1.0f - shadow_strength, 1.0f, lit_ratio);
```
ハードウェア $2 \times 2$ 補間と $3 \times 3$ PCF が合わさることで、実質 $4 \times 4$ 相当の極めて滑らかな半影（Penumbra）が生成されます。

#### 3. 環境光との物理的な調和
影の中にある物体も真っ暗にはならず、周囲の散乱光（環境光）でほんのり見えなければ不自然です：
```hlsl
// 直接光（拡散＋鏡面反射）にのみ shadow_factor を乗算
float3 direct_light = (diffuse + specular) * shadow_factor;
// 環境光 (ambient) は影の影響を受けずに加算
float3 final_rgb = base_color.rgb * (ambient + direct_light);
```
これにより、影の中でも木箱やチェッカーボードの模様が自然に視認できます。

### 10.5. シャドウアクネとピーターパニングの防止 (Depth Bias)
シャドウマッピング特有の 2 大アーティファクトである「シャドウアクネ」と「ピーターパニング」に対し、2 重の対策を施しています：

1. **シャドウアクネ (Shadow Acne)**:
   - 深度マップの数値精度誤差とサンプリング解像度のズレにより、平面上に黒い縞模様（自己遮蔽のノイズ）が発生する現象。
   - **対策**:
     - `ShadowPipeline` のラスタライザステートにハードウェアスロープスケーリングバイアスを設定 (`DepthBias = 100`, `SlopeScaledDepthBias = 1.5f`)。面の傾きが大きいポリゴンほど自動的に深度値を奥にオフセット。
     - ピクセルシェーダ側でも `current_depth - bias` による定数バイアス（初期値 `0.0015f`）を適用。
2. **ピーターパニング (Peter Panning)**:
   - バイアスを過剰に大きく設定すると、影が物体の足元から離れて物体が宙に浮いているように見えてしまう現象。
   - **対策**:
     - ImGui インスペクタからバイアス値を `0.0001` 刻みで微調整可能にし、アクネが消える最小限のバイアスをインタラクティブに決定可能に設計。

### 10.6. ImGui によるリアルタイムシャドウ調整
`DirectionalLight3D` ノードにシャドウ調整用アクセサを用意し、ImGui インスペクタから以下のパラメータを即座に変更できるようにしました：
- **シャドウバイアス (Shadow Bias)**: 自己遮蔽縞の除去と足元の接地感の微調整（スライダー: `0.0001` 〜 `0.01`）。
- **影の濃さ (Shadow Strength)**: 影の落ち込み度合い（スライダー: `0.0`（影なし）〜 `1.0`（完全な黒））。
- **シャドウ範囲 (Shadow Box Size)**: 光源の直交投影範囲（スライダー: `5.0` 〜 `50.0`）。範囲を絞るほど影の解像度が上がり鮮明になります。
